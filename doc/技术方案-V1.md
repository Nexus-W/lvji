### 0.1 你的角色与边界

你要实现的是一个 **Flutter 本地旅行相册 App**，Android 优先，代码需同时能编译到 iOS。

**必须遵守：**

1. **不要发明本文档没有的功能。** 需要但没写的，先按"最小实现"处理，并在代码注释里标 `// TODO(未定义): ...`，不要自行扩展。

## 1. 项目定位与 V1 范围

### 1.1 一句话

把一段旅行的照片，按**行程 → 天 → 地点**收拢起来，让你半年后还能找回"这是在洱海哪一段"。

### 1.2 用户与场景

- 一次旅行拍 500–3000 张：手机、相机、无人机、朋友微信传的。
- 回来后照片散在系统相册里，与技术无关的痛点是**找不回上下文**。
- 目标用户不写手账、不做后期，只想"翻得回来"。

### 1.3 V1 做什么

| 模块 | 内容 |
|---|---|
| 行程 | 新建 / 改名 / 改起止日期 / 删除（进回收站） |
| 导入 | 从系统相册多选、指定目标行程、导入前分组预览 |
| 分组 | 按 EXIF 拍摄日期归到对应天；无时间的单独一桶 |
| 时间轴 | 按天展示、按日期/地点切换分组、展开全部 |
| 大图 | 查看、写备注、设为封面、加入精选、删除（二次确认） |
| 地图 | 照片按坐标聚合成点、滑动联动、点开大图 |
| 足迹 | 所有行程的城市点（同一套地图组件，缩到世界尺度） |
| 修正 | 缺坐标的照片集中补救（地图点选 / 搜地名） |
| 分享 | 九宫格拼图导出（手选 9 张，可跨行程），支持深浅两套样式 |
| 设置 | 数据占用、清理缓存、关于（从行程列表「＋」菜单进入） |

### 1.4 V1 明确不做

- 视频（缩略图、播放、元数据全部延后）
- 账号 / 云同步 / 多设备
- 地图 SDK（见 §6.3，自绘）
- 富文本手记（纯文本，最多 500 字）
- 分享到第三方平台的 SDK 集成（用系统分享面板）
- iPad / 横屏适配（锁定竖屏）
- 国际化（仅简体中文）

### 1.5 为什么这么砍

每一项被砍的功能都会带来独立的权限、依赖、UI 分支。
**V1 的目标是"导入 → 看 → 挑"这条主链路稳，不是功能全。**

## 2. 技术选型

### 2.1 框架

| 项 | 决定 | 理由 |
|---|---|---|
| 框架 | Flutter 3.24+ / Dart 3.5+ | 一套代码双端；本地重绘性能足够 |
| 最低版本 | Android 8.0 (API 26) / iOS 15.0 | Photo Picker 与文件 API 的下限 |
| 状态管理 | `ChangeNotifier` + `provider` | 页面 6 个，不需要 Riverpod/Bloc |
| 本地存储 | `sqflite` + `path_provider` | 结构化查询（按天/按地点聚合） |
| 图片处理 | `photo_manager` 仅用于读 EXIF 缩略图？**不用**，见 2.2 | — |

**禁止引入**：Riverpod、Bloc、GetX、Hive、Isar、Firebase、Sentry、任何统计 SDK。

### 2.2 相册访问（关键决策）

**用 `image_picker` 的 `pickMultiImage()`，不要用 `photo_manager`。**

理由：

- `image_picker` 在 Android 13+ 走系统 **Photo Picker**、iOS 走 **PHPicker**，
  **不需要任何相册权限**，不弹授权框，上架审核也少一轮问询。
- `photo_manager` 需要 `READ_MEDIA_IMAGES`，用户一旦拒绝就要做引导页，是额外的一条分支。

代价：拿不到"整个相册的时间线"，只能拿到用户手选的。**这个代价可以接受**——我们的场景本来就是"导入一次旅行"，不是"浏览整个相册"。

### 2.3 依赖清单（锁定版本，不要升级到 latest）


## 4. 数据模型

### 4.1 表结构（SQLite）

```sql
PRAGMA foreign_keys = ON;

-- 行程
CREATE TABLE trips (
  id           TEXT PRIMARY KEY,           -- uuid v4
  name         TEXT NOT NULL,
  start_date   TEXT NOT NULL,              -- 'YYYY-MM-DD'
  end_date     TEXT NOT NULL,
  country      TEXT,                       -- 可空：新行程还没有坐标
  province     TEXT,
  city         TEXT,
  lat          REAL,
  lng          REAL,
  note         TEXT NOT NULL DEFAULT '',   -- 手记，纯文本 <= 500 字
  cover_photo  TEXT,                       -- photos.id，可空
  deleted_at   TEXT,                       -- 软删；NULL = 正常
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL
);
CREATE INDEX idx_trips_alive ON trips(deleted_at);

-- 天（由 start/end 生成，行程改日期时重建）
CREATE TABLE days (
  id       TEXT PRIMARY KEY,
  trip_id  TEXT NOT NULL REFERENCES trips(id) ON DELETE CASCADE,
  date     TEXT NOT NULL,                  -- 'YYYY-MM-DD'
  place    TEXT NOT NULL DEFAULT '',
  sort     INTEGER NOT NULL
);
CREATE UNIQUE INDEX idx_days_unique ON days(trip_id, date);

-- 照片
CREATE TABLE photos (
  id          TEXT PRIMARY KEY,
  trip_id     TEXT NOT NULL REFERENCES trips(id) ON DELETE CASCADE,
  day_id      TEXT REFERENCES days(id) ON DELETE SET NULL,  -- 无时间 = NULL
  uri         TEXT NOT NULL,               -- 本地文件或 content://
  hash        TEXT NOT NULL,               -- 文件 SHA1，用于去重
  taken_at    TEXT,                        -- ISO8601，可空
  lat         REAL,
  lng         REAL,
  place       TEXT,                        -- 反查/用户填写的地名
  width       INTEGER NOT NULL,
  height      INTEGER NOT NULL,
  is_cover    INTEGER NOT NULL DEFAULT 0,
  is_featured INTEGER NOT NULL DEFAULT 0,
  note        TEXT NOT NULL DEFAULT '',
  deleted_at  TEXT,
  created_at  TEXT NOT NULL
);
CREATE UNIQUE INDEX idx_photos_dedup ON photos(trip_id, hash);  -- 同一行程内同图只入一次
CREATE INDEX idx_photos_trip ON photos(trip_id, deleted_at);
CREATE INDEX idx_photos_day ON photos(day_id);

-- 导入批次（只做统计与回溯，不参与张数计算）
CREATE TABLE imports (
  id       TEXT PRIMARY KEY,
  trip_id  TEXT NOT NULL REFERENCES trips(id) ON DELETE CASCADE,
  count    INTEGER NOT NULL,
  at       TEXT NOT NULL
);
```

### 4.2 三条硬约束（对应 §8 的已知问题）

**① 级联删除**

`days` / `photos` / `imports` 全部 `ON DELETE CASCADE`。
删行程时**物理删除**（不是软删），因为用户明确点了"删除这个行程"，回收站只给"删照片"用。

> 若要做行程回收站，改成 `deleted_at` + 定时清理；V1 不做，直接物理删。

**② 照片张数以 `photos` 表为准**

**永远不要**用 `imports.count` 累加得出"这个行程有多少张"。

```dart
Future<int> countOf(String tripId) async {
  final r = await db.rawQuery(
    'SELECT COUNT(*) c FROM photos WHERE trip_id = ? AND deleted_at IS NULL', [tripId]);
  return Sqflite.firstIntValue(r) ?? 0;
}
```

这一条直接消灭了原型里"重复导入导致张数翻倍"的 bug。

**③ 唯一索引去重**

`UNIQUE(trip_id, hash)`。导入时用 `INSERT OR IGNORE`，重复照片自动跳过，并在导入结果里显示"N 张已存在，已跳过"。

### 4.3 日期与"天"的生成

```
行程 start=2026-10-02, end=2026-10-06
→ 生成 5 条 days：10-02 / 10-03 / 10-04 / 10-05 / 10-06
```

改日期时：保留已有 `days`（按 date 匹配），新增缺的、删除多余的。
删除某天时，该天的 `photos.day_id` 置 NULL（`ON DELETE SET NULL`），照片不会丢，落回"未分组"。

### 4.4 照片分组算法（导入时）

```dart
String? pickDayId(DateTime? takenAt, List<Day> days) {
  if (takenAt == null) return null;              // → 时间未知
  // 规则：凌晨 0:00–4:00 算前一天（用户心理上还在"昨晚"）
  final d = takenAt.hour < 4 ? takenAt.subtract(const Duration(days: 1)) : takenAt;
  final key = DateFormat('yyyy-MM-dd').format(d);
  for (final day in days) {
    if (day.date == key) return day.id;
  }
  return null;                                    // 不在行程范围内 → 未分组
}
```

**行程范围外的照片不要硬塞。** 归到"未分组"，在预览里提示"N 张不在行程时间内"。

## 5. 核心流程

### 5.1 导入链路

```
[行程列表 +] → [导入页]
   ① 选目标行程（默认最近一次的行程，可切换）
   ② 点「选择照片」→ image_picker.pickMultiImage()
   ③ 逐张读 EXIF：takenAt / lat / lng / 宽高
   ④ 算 hash（SHA1，读文件流）
   ⑤ 查重：同行程内 hash 已存在 → 标记"已存在"
   ⑥ 点「导入」→ 弹分组预览：
        10月2日 · 大理古城   14 张
        10月3日 · 洱海东岸    8 张
        时间未知              2 张（其中 1 张已存在，将跳过）
   ⑦ 确认 → 事务写入 photos + imports → 结果页
   ⑧ 结果页：「查看行程」/「补这 N 张的位置」
```

**性能要求**：

- 读 EXIF 与算哈希必须在 `Isolate` 里跑（`compute`），主线程不能卡。
- 100 张照片的导入应在 3 秒内完成（中端机）。
- 超过 500 张时，预览只显示前 3 天 + "其余 N 天"，不要一次渲染几十行。

**失败处理**：

- 单张读取失败（文件损坏/权限失效）→ 跳过，计入"失败 N 张"，不中断整批。
- 全部失败 → 提示"没有可导入的照片"，留在导入页。

### 5.2 接收"分享到旅迹"

```xml
<!-- android/app/src/main/AndroidManifest.xml -->
<intent-filter>
  <action android:name="android.intent.action.SEND"/>
  <action android:name="android.intent.action.SEND_MULTIPLE"/>
  <category android:name="android.intent.category.DEFAULT"/>
  <data android:mimeType="image/*"/>
</intent-filter>
```

流程：

```
微信「分享」→ 选「旅迹」
  → 拿到 content:// 列表（自带临时读权限，不要申请相册权限）
  → 复制到 App 私有目录？不需要：content URI 在本次会话内可读
  → 读 EXIF（微信图通常没有时间/坐标）
  → 直接进「导入预览」，默认目标行程 = 最近一次
  → 用户可改日期归属
```

**注意**：URI 的读权限在进程结束后失效，**必须在接收后立即把文件复制到 App 私有目录**（`getApplicationDocumentsDirectory()/imports/`），否则下次打开图片会失效。

> 这条是硬要求。原型里没做，但真实实现必须做。

### 5.3 删除链路

```
大图「删除」→ 确认弹窗（说明"只从本行程移除，原图仍在相册"）
  → photos.deleted_at = now()   （软删）
  → 7 天后回收站清理任务物理删除记录（只删记录，不删原图）
```

**选片模式批量删除**：同一个确认弹窗，标题带张数。

**原图永远不动。** 我们只管理索引。

### 5.4 信息修正链路

一个弹层，两个入口：

```
大图「修改」        → PhotoInfoSheet(photo)
补救页点一张        → PhotoInfoSheet(photo, focusMap: true)
```

弹层内容：

- 拍摄时间（日期 + 时间选择器，可清空）
- 地点（文本框 + 「在地图上点选」）
- 地图点选 → 反查地名（V1 用本地地名表做最近匹配，不做逆地理编码请求）

保存后：

- 若时间变化 → 重新计算 `day_id`
- 若坐标变化 → 更新 lat/lng
- 从补救队列移除（`lat IS NULL OR lng IS NULL` 的集合自动缩小）

### 5.5 分享九宫格

```
行程「⋯」→「分享精选九宫格」
  → 默认取：本行程精选（最多 9）→ 不足补最近导入
  → 画布 1080×1080，3×3，间隙 2px
  → 底部信息条：行程名 / 日期 / 「旅迹」（可关闭）
  → 「选照片」可跨行程混选，最多 9 张
  → 保存：RepaintBoundary.toImage(pixelRatio: 3) → 存相册
```

**硬要求**：导出 1080×1080，PNG，无压缩伪影。这是微信朋友圈的无损上限。

### 6.3 地图：自绘，不接 SDK

**决定：V1 地图用 `CustomPaint` 自绘 + 内置世界底图矢量，不接高德/腾讯/Google。**

理由：

- 接 SDK 要申请 key、要联网、要处理国内坐标系偏移（GCJ-02 vs WGS-84），
  还要处理 SDK 的隐私合规弹窗（上架必查）。**这四件事每一件都能拖一周。**
- 我们的地图只有两个用途：① 看清照片在行程内的分布 ② 看自己去过哪些城市。
  这两件事 **自绘完全够用**，而且离线、零成本、零权限。

实现要点：

- 底图：内置一份简化世界地图矢量（原型里的点阵大陆，坐标已按经纬度换算）
- 投影：等距圆柱 `x = (lng+180)/360*W`，`y = (90-lat)/180*H`
- 两个尺度：`trip`（缩放到行程范围）/ `world`（全球）
- 手势：拖动平移、双指缩放，**不做惯性**（V1 够用）
- 照片点：按坐标聚类，同时刻移动 < 20px 的合并为一个点并显示数量

> 如果后续要接真地图，只需要替换 `MapCanvas` 一个文件，其它页面不动。这是自绘的额外好处。

## 8. 已知问题与对策（逐条验收）

> 这些是原型阶段已经踩过或预见的坑。**每一条都要在 V1 里对应解决，并有可执行的验收方式。**

### 8.1 传错行程 id 会静默打开第一趟

**现象**：`getTrip(id)` 找不到时返回 `TRIPS[0]`，用户删了行程再从返回栈进入，会打开别的行程。

**对策**：

```dart
Future<Trip?> findTrip(String id) async { ... }   // 返回可空，不兜底
```

页面入口统一判断：

```dart
final trip = await repo.findTrip(id);
if (trip == null) {
  if (mounted) Navigator.of(context).pushReplacementNamed('/trips');
  return;
}
```

**验收**：手动构造一个不存在的 id 打开详情页 → 应跳回列表，不显示任何行程。

### 8.2 删行程遗留脏数据

**对策**：外键 `ON DELETE CASCADE` + 物理删除（见 §4.2）。
另加启动时一致性检查（Debug 构建）：统计 `photos` 里不存在 `trip_id` 的孤儿记录，应为 0。

**验收**：建一个行程 → 导入 5 张 → 删行程 → 查库，`photos` 中 `trip_id` 为该行程的记录数 = 0。

### 8.3 重复导入导致张数翻倍

**对策**：`UNIQUE(trip_id, hash)` + `INSERT OR IGNORE`；张数一律 `COUNT(*)`。

**验收**：同一批 10 张导入两次 → 第二次结果页显示"10 张已存在，已跳过"，行程总张数仍为 10。

### 8.4 新建行程没有坐标，地图/足迹里消失

**对策**：

- `trips.lat/lng` 允许 NULL
- 足迹页只画有坐标的行程，并在底部提示"还有 N 个行程没有位置"（可点进补）
- 不要静默过滤

**验收**：新建一个空行程 → 足迹页城市数不变，但出现"1 个行程没有位置"的提示。

### 8.5 分享选片只存了颜色，没有原图引用

**对策**：`ShareItem { photoId, uri }`，不允许只存展示信息。
九宫格渲染时按 `photoId` 取真实文件。

**验收**：跨行程选 3 张 → 导出后打开图片，3 张内容与所选一致。

### 8.6 微信传来的照片没有时间/坐标

**对策**：见 §5.2。导入预览里明确列出"时间未知 N 张"，并允许用户**手动指定归到哪一天**。

**验收**：从微信分享 3 张图到 App → 预览显示"时间未知 3 张"→ 手动选"10月3日"→ 导入后落在那天。

### 8.7 导入时主线程卡死

**对策**：EXIF + 哈希在 Isolate；UI 显示进度"正在读取 12/86"。

**验收**：100 张导入过程中，下拉列表仍可滚动（不冻结）。

### 8.8 大图里"改地点"和补救页"改地点"是两个界面

**对策**：只有一个 `PhotoInfoSheet`，两个入口。

**验收**：从大图改地点、从补救页改地点，界面完全一致，改完两边数据同步。

### 8.9 弹层/头部样式各页不一致

**对策**：六条红线（§6.2）。

**验收**：`grep -r "showModalBottomSheet(" lib/features` 结果为 0（全部走 AppSheet）。

### 8.10 九宫格导出模糊

**对策**：`RepaintBoundary.toImage(pixelRatio: 3)`，画布逻辑尺寸 360×360 → 实际 1080×1080。

**验收**：导出图片属性为 1080×1080，放大看边缘清晰。
